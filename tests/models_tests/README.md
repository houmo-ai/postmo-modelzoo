# `models_tests` 模型回归测试说明

本文档对应当前 `tests/models_tests` 重构后实现。测试由模型 JSON 配置驱动，pytest 入口只负责选择模型和 flow；下载、量化、编译、artifact 复用、demo、精度与性能校验均由 flow handler 和公共 workflow 组件完成。

pytest 可见的七类 flow 为：

```text
get_model -> quant -> compile -> demo -> compare -> eval -> perf
```

其中：

- `demo_multibatch` 是 `demo` 的附加 case，不生成独立测试文件；
- CV 注册七个 flow；
- LLM 当前只注册 `get_model`、`quant`、`compile`、`demo`、`perf`，不支持 `compare` 和 `eval`；
- 一个模型的不同 flow 可以分别使用 Python 脚本或 HMATC，实现自由混搭。

### 1.4 与 `tests/tests_utils/` 的关系

`models_tests` 不再自行实现通用 subprocess、workspace、平台、marker 和虚拟环境能力，主要复用：

- `command_execution.py`：实时读取 stdout/stderr、写日志、可选终端镜像、超时和进程组清理；
- `runtime_context.py`：解析 backend、release、cache 根目录和 separate 阶段；
- `workspace.py`：复制模型源码到源目录旁的临时 workspace，通过 `.imodelzoo-workspace` sentinel 保证只清理框架拥有的目录；
- `python_environment.py`：创建/复用项目测试虚拟环境并安装 requirements；
- `pytest_support.py`：要求每个生成用例恰好有一个 `ndevice_*` 和一个 `dev_mem_*` marker；
- `platform_device.py`、`resource_lock.py`：平台/设备检测与跨 flow cache 锁。

## 2. 测试生成、调用链和依赖

### 2.1 调用链

生成的测试函数最终执行：

```text
test_<flow>_models.py
  -> test_models_utils.execute_<flow>_flow()
  -> execute_model_flow()
  -> ModelConfigRepository.load()
  -> TestRuntimeContext.from_environment()
  -> create_flow_context()
  -> FLOW_REGISTRY.resolve(family, backend, flow)
  -> handler.run(FlowRequest, FlowServices)
  -> FlowResult
  -> pytest pass / skip / fail
```

每个命令都带有稳定诊断字段：

```text
run_id model family backend flow case_id phase
```

配置错误、artifact 错误、命令基础设施错误会在 pytest 边界被格式化；handler 返回的业务校验失败会转为不带冗长 Python traceback 的 pytest failure。

### 2.2 生成规则

`update_test_py.py` 对所有非模板配置执行全量生成：

- 文件名 `model_cfg_<name>.json` 决定传给执行器的模型名；
- marker 将 `-` 转为 `_`，`.` 转为 `dot`，例如 `qwen3.5 -> qwen3dot5`；
- 测试函数类别来自 `model_dir` 的第二段，例如 `models/segmentation/sam2` 生成 `test_segmentation_sam2_<flow>`；
- 每个模型、每个受支持 flow 只生成一个 pytest 函数，具体参数 case 在 handler 内执行；
- `demo_multibatch` 不生成独立函数；
- `obsolete: true` 仍保留测试函数和 marker，运行时再 skip；
- `--check` 不修改文件，只报告过期文件、增删行和增删测试函数；
- 普通执行会全量重写生成文件，因此可以修正 JSON 与现有 `test_<flow>_models.py` 不一致的情况。

### 2.3 固定顺序与 pytest dependency

`conftest.py` 将收集结果按以下文件顺序排列：

```text
get_model -> quant -> compile -> demo -> compare -> eval -> perf
```

生成器按代码侧 `FLOW_DEPENDENCY_RULES` 添加 pytest-dependency：

| 当前 flow | 依赖规则 |
| --- | --- |
| `get_model` | 无前置依赖，但注册稳定 dependency name。 |
| `quant` | 当前模型支持 `get_model` 时依赖它。 |
| `compile` | 优先依赖 `quant`；不支持 quant 但支持 get_model 时依赖 get_model。 |
| `demo/compare/eval/perf` | 不创建 pytest dependency edge；handler 自行检查、复用或准备所需 artifact。 |

同一个模型在不同 backend 上生成的是同一个 pytest node，因此 quant/compile 的静态依赖必须在各 backend 上一致；配置加载时会检查这一点。

由于不同 flow 会共享 cache 和 artifact，当前不支持 `pytest -n 2` 等多 worker 执行；不使用 xdist或仅使用一个 worker。

## 3. 运行上下文、环境变量和执行模式

### 3.1 常用命令

以下命令从 `/data02/services/imodelzoo` 执行，运行前按项目要求加载环境：

```bash
pytest -s -v tests/models_tests/
pytest -s -v tests/models_tests/ -m "sam2"
pytest -s -v tests/models_tests/ -m "demo"
pytest -s -v tests/models_tests/ -m "sam2 and demo"
pytest --log-cli-level=INFO -s -m "imodelzoo and ndevice_1 and dev_mem_12g"

python -m tests.models_tests.update_test_py
python -m tests.models_tests.update_test_py --check
pytest tests/models_tests --collect-only -q
```

### 3.2 环境变量

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `HOUMO_TARGET` | `xh2` | 当前 backend。默认值不仅保存在 runtime context，也会同步进父进程环境，保证 `get_model.py`、`ptq.py`、`build.py`、`demo.py` 子进程看到相同 backend。 |
| `USE_RELEASED_MODELS` | `ON` | `ON/on` 为 release 模式；其他值为 development 模式。 |
| `SKIP_INFER` | 未设置 | 值为字符串 `ON` 或 `OFF` 时启用 separate；是否为 no-infer/infer 不由 ON/OFF 区分，而由当前是否 ASIC 决定。 |
| `IMODELZOO_MODELS_PATH` | `tests/models_<backend>` | `cached_models` 的物理根目录。 |
| `HOUMO_EXAMPLES_PATH` | 仓库根目录 | `hm_gptq` 额外 requirements 的基准路径。 |
| `HOUMO_DATASETS_PATH` | `<repo>/data/datasets` | 数据集路径，也用于解析 quant `prerequisites.py_reqs` 的相对文件。 |
| `HOUMO_FULL_DATASET` | 未设置 | 设置后 eval 使用 JSON 中完整阈值；未设置时阈值乘 `0.5`。 |
| `IMODELZOO_ALLOW_XH2_NCORE4` | `OFF` | `ON` 时允许执行默认被过滤的 xh2 `ncore=4` HMATC build case。 |
| `IMODELZOO_MIRROR_COMMAND_OUTPUT` | `ON` | 是否把模型命令 stdout/stderr 在写入日志的同时镜像到 pytest 进程。 |

`results_path` 当前没有独立环境变量，固定为 `tests/model_results_<backend>`。

### 3.3 default、no-infer 和 infer

| 条件 | `TCaseType` | 主要行为 |
| --- | --- | --- |
| `SKIP_INFER` 未设置或不是 `ON/OFF` | `DEFAULT` | 当前机器完成完整 flow；inference handler 可复用 cache，也可调用上游准备缺失 artifact。 |
| `SKIP_INFER=ON/OFF`，当前不是 ASIC | `SEPARATE_NO_INFER` | 执行 get_model/quant/compile；demo/compare/eval/perf 只准备和持久化推理所需 artifact，不执行真正 inference，最终以 `PREPARED_ONLY` 转为 pytest skip。 |
| `SKIP_INFER=ON/OFF`，当前是 ASIC | `SEPARATE_INFER` | get_model/quant/compile 认为 no-infer 已执行并 skip；demo/perf 等恢复缓存后执行推理。 |

注意：`ON` 和 `OFF` 都只是兼容旧接口的“启用 separate”值，并不分别代表两个阶段。阶段由 `is_asic_platform()` 选择。

### 3.4 release 模式

当前默认就是 release 模式。主要差异为：

- LLM `get_model` 过滤 `type=raw`，所有 family 都过滤 `source_type=modelscope` 的 release case；
- LLM Python quant 只允许 development + GPU，因此 release 下 skip；
- LLM compile 在 release 下 skip，CV compile 不因此 skip；
- inference 会把匹配的 `get_model type=hmm` 下载映射到最终 `cached_results` case；仅目标 HMM 目录缺失时下载，不会无条件重复下载；
- `enable_demo_test=false` 只在 release 下生效：ASIC `test.sh` 阶段结束后不再执行标准 Python/HMATC demo；development 模式仍执行后续 demo；
- perf 的最低通过比例由 development 的 `95%` 降为 release 的 `10%`。

## 4. workspace、缓存和 artifact

### 4.1 workspace

每个 flow 都把 `model_dir` 指向的模型源码复制到临时 workspace 后再执行命令，不直接修改模型源码目录。默认 workspace 位于模型目录旁，名称包含模型、phase 和时间戳；退出时只有存在 `.imodelzoo-workspace` sentinel 且路径在允许根目录内才会被删除。

`test.sh` 使用单独的 `demo_test_sh` workspace，标准 demo 使用另一个 `demo` workspace，两者相互隔离，但命令结果最终都计入同一个 demo flow。

### 4.2 两个缓存根

对于配置：

```json
{
  "model_dir": "models/llm/example",
  "dependencies": {
    "ndevice": [1],
    "dev_mem": ["12g"]
  }
}
```

默认物理目录为：

```text
cached_models
  -> tests/models_<backend>/models/llm/example

cached_results
  -> tests/model_results_<backend>/ndevice_1_dev_mem_12g/models/llm/example
```

JSON 命令参数中只写逻辑路径：

```text
cached_models/<case-or-resource>
cached_results/<case>
```

替换按完整路径段进行，`old_cached_models` 这类只包含相同字符串的名称不会被误替换。

通常职责为：

- `cached_models`：get_model 下载目录、raw ONNX、tokenizer/Hugging Face 模型，以及 get_model 对 workspace 的副作用文件；
- `cached_results`：量化/编译结果和 inference 最终消费的持久 artifact。

如果 Python `compile_params.output_dir` 写在 `cached_models/<case>`，框架会把有效 HMM 镜像到 `cached_results/<case>`。infer 校验和消费最终的 `cached_results`，不要求 producer 侧目录在 no-infer 与 infer 机器上始终同时存在。

### 4.3 manifest、复用与原子发布

下载、量化和编译目录可包含：

```text
artifact_manifest.<artifact_type>.<case_id>.json
```

旧的 `artifact_manifest.json` 仍兼容。manifest 包括：

- `schema_version`、`fingerprint_version`；
- `artifact_type`、`model_name`、`model_family`、`backend`、`case_id`；
- `producer_flow`、`source_type`；
- `config_fingerprint`；
- `required_files`。

cache 检查会区分 valid、legacy、missing、invalid 等状态。Python quant/build 和 HMM 镜像使用 staging + backup 原子发布：命令或校验失败不会直接覆盖原来的有效目录；上次进程在替换中断时，下次可以恢复受框架标记的 backup。

### 4.4 separate-infer 中的 `cached_models` 补全

separate-infer 在执行 demo/perf 前会扫描实际 `demo_params` 和 `demo_multibatch_params` 参数行中的 `cached_models/<folder>` 引用：

1. 目录存在且至少有一个非空 artifact 文件：直接复用，不下载；
2. 目录缺失或为空：根据同一参数行中的 `model_name`、`model_size`、`context_length`、`prefill_length`、`batch`、`ndevice`、`ncore` 等字段匹配 `get_model_params.type=hmm` case；
3. 只执行匹配的 HMM get_model case；
4. 下载后再次检查每个引用目录；仍未生成时明确失败并打印缺失路径。

这类 `cached_models` 目录通常是 tokenizer 或 Hugging Face 资源。它与 `cached_results` 中的最终 HMM artifact 是两种不同需求。

## 5. 各 flow 当前行为

### 5.1 `get_model`

- 参数来自当前 backend 的 `get_model_params`；
- 每个 case 执行 `python3 get_model.py`；
- 单条命令超时为 4 小时；
- `type=raw/quant/hmm` 分别发布 raw、quant、compiled artifact；
- HMM 成功后必须包含至少一个非空 `.hmm` 文件；
- 作为 quant/compile/inference 的内部上游调用时，会对 workspace 前后做快照，将新增或变化文件按相对路径持久化到 `cached_models`；
- separate-infer 的顶层 get_model 测试直接 skip。

### 5.2 `quant`

quant 总是先确保 `get_model type=raw`：

```text
有 hmquant_params -> hmatc quant
否则             -> Python ptq.py
```

Python quant：

- LLM 需要 GPU 且仅 development 执行；
- 使用 `requirements_ptq.txt`、`requirements.txt` 和 `prerequisites` 准备环境；
- 支持 `out-dir`、`output_dir`、`out_dir`、`output_path` 作为输出字段；
- 输出目录必须位于 `cached_results`，并通过原子 writer 发布。

HMATC quant 会忽略 JSON 中的 `onnx` 字段，由 HMATC/配置文件使用固定路径取得原始 ONNX。

### 5.3 `compile`

```text
有 hmbuild_params -> raw get_model -> HMATC quant -> HMATC build
否则              -> 确保 quant model -> Python build.py
```

- HMATC build 按 `hmbuild_params.<backend>` 矩阵逐 case 测试；非 ASIC 自动增加 `--skip_check`；
- xh2 `ncore=4` 默认过滤，除非设置 `IMODELZOO_ALLOW_XH2_NCORE4=ON`；如果全部 case 被过滤，明确 skip；
- ASIC 上 HMATC build 会解析 cosine 输出，默认阈值 xh1=`0.99`、xh2=`0.90`；
- Python build 在输入 `model_dir` 缺失时直接报告具体 case 和路径；
- Python build 会复用有效 compiled manifest，并把 `quant_*.pt` sidecar 放到输出的 `hmquant/`；
- LLM release、aarch64 和 separate-infer 不执行 compile。

### 5.4 `demo`

demo 由两个阶段组成：

1. ASIC 上可选的 `test.sh`；
2. 标准 HMATC 或 Python demo。

标准实现选择规则：

```text
存在 hmdemo_params 且不是 aarch64 -> hmatc demo
否则                               -> demo.py / 自定义 script
```

Python demo 会执行 `support_flow` 中声明的 `demo`，并在声明 `demo_multibatch` 时继续执行对应参数。`demo_params.script` 或 `demo_multibatch_params.script` 可以覆盖默认的 `demo.py`、`demo_multibatch.py`。

`test.sh` 和标准 demo 的失败分别记录；框架检查非零退出码和通用 `Fail`/`[error]` 输出标记。Python demo或 `test.sh` 失败时，日志中还会记录 argv、cwd、返回码、耗时以及 stdout/stderr 最后 4000 个字符。少量会正常打印 `Fail` 的模型例外保存在代码 policy 中，不写进 JSON。

### 5.5 `compare`

- 仅 CV 注册；
- 需要 `hmcompare_params`；
- 执行 `hmatc compare` 并解析结果表；
- 默认 cosine 阈值 xh1=`1.0`、xh2=`0.90`，可由 `validation` 覆盖；
- xh1 明确不支持 separate compare；
- aarch64 不执行。

### 5.6 `eval`

- 仅 CV 注册；
- 需要 `hmeval_params` 和非空 `eval_threshold`；
- 每个参数 case 先额外带 `--onnx` 执行 ONNX eval，再执行 HM eval；
- 从 stdout 解析配置中的每个指标，逐 case 校验 `hm >= onnx * threshold`；
- 未设置 `HOUMO_FULL_DATASET` 时 threshold 乘 `0.5`；
- case 数不一致或任一侧缺少指标都会明确失败；
- aarch64 不执行。

### 5.7 `perf`

`perf_metrics` 是必需的性能基线。runner 选择为：

```text
perf_params == "demo" -> 复用 demo_params 第一个 case
代码侧 custom override -> 执行指定 Python 脚本
其他情况               -> hmatc perf，参数来自 hmperf_params
```

默认从完整用例日志解析指标；代码侧也可指定 stdout、stderr 或 combined output。默认指标 key：

| JSON 指标名 | 默认日志 key | 方向 | 聚合 |
| --- | --- | --- | --- |
| `qps` | `[Throughput] qps` | 越高越好 | max |
| `prefill` | `Prefill Speed` | 越高越好 | max |
| `decode` | `Decode Speed` | 越高越好 | max |
| `end2end` | `E2E TPS` | 越高越好 | max |

特殊日志格式、lower-is-better 指标或 custom runner 写在 `perf_metric_validation.py`，不扩展 JSON 为执行 DSL。development 要求达到基线的 `95%`，release 要求 `10%`；lower-is-better 指标使用对应上限换算。

## 6. HMATC inference、混合 flow 与多 YAML

### 6.1 混合 flow 选择

每个 flow 根据自己的参数 section 选择实现：

| flow | Python/模型脚本 | HMATC |
| --- | --- | --- |
| `get_model` | `get_model.py` | 无独立 HMATC get_model。 |
| `quant` | `quant_params` -> `ptq.py` | 存在 `hmquant_params` 时使用 `hmatc quant`。 |
| `compile` | `compile_params` -> `build.py` | 存在 `hmbuild_params` 时使用 HMATC quant/build。 |
| `demo` | `demo_params` -> `demo.py` 或 `script` | 存在 `hmdemo_params` 且非 aarch64 时使用 `hmatc demo`。 |
| `compare` | 无通用 Python compare | CV `hmcompare_params`。 |
| `eval` | 无通用 Python eval | CV `hmeval_params`。 |
| `perf` | `perf_params: "demo"` 或代码侧 custom runner | 默认 `hmperf_params`。 |

`support_flow` 决定是否生成和运行某个 pytest flow；`support_hmatc` 目前是兼容性的能力描述字段，运行时真正选择实现的是对应参数 section 是否存在。

例如 SAM2 可以保持：

```text
get_model -> get_model.py
quant     -> HMATC
compile   -> HMATC
demo      -> demo.py
```

无需为“混合模式”增加新的 JSON 开关。

### 6.2 inference 使用的 HMATC bundle

对于存在 `hmbuild_params` 的 demo/perf/eval/compare，inference 准备不是简单假设只有一个 `config.yml`：

1. 从 `hmquant_params` 和当前 backend 的 `hmbuild_params` 中收集所有 `config` 值；
2. 去重后依次对每个 YAML 执行默认 inference `hmatc quant` 和 `hmatc build`；
3. 所有 YAML 必须位于 workspace 内；
4. 每个 YAML 的 `model.save_dir` 必须存在且所有组件相同；
5. 最终 bundle 位于 `<model.save_dir>/<backend>`，要求同时包含非空 HMM 和 `hmquant/*with_act.onnx`；
6. YAML 内容、相对路径、backend 和命令组成 fingerprint；有效 bundle 可直接恢复复用。

这使 encoder/decoder 等多组件模型可以使用自定义 YAML 名称和嵌套目录，同时仍发布为一个 `inference-default` compiled artifact。

### 6.3 raw ONNX 与 separate

HMATC 工具使用固定输入/输出布局，因此框架负责在阶段之间搬运文件：

#### DEFAULT 或 SEPARATE_NO_INFER

```text
get_model.py --type raw
  -> 记录 workspace 中新增/修改的文件
  -> 按相对路径保存到 cached_models
  -> 恢复或生成 HMATC inference bundle
```

即使 `cached_results` 已经存在可复用 HMATC bundle，也会先执行 raw get_model，避免 demo/perf/eval/compare 缺少原始 ONNX 或配套文件。

#### SEPARATE_INFER

```text
cached_models 完整目录树
  -> 递归复制到新 workspace
  -> 保持 raw get_model 产物的原始相对目录

cached_results
  -> 恢复 HMATC YAML、save_dir 输出和相关 artifact
```

复制时会排除 cache 根目录的 `lock.lock` 和 `artifact_manifest*` 协调文件。这样无需 HMATC 支持自定义输入、输出路径。

## 7. `test.sh` 与标准 demo

`test.sh` 是 demo flow 内的一段端到端功能检查，设计与现有 LLM 模型保持一致：

- 只在 ASIC 且模型目录存在 `test.sh` 时执行；
- `SEPARATE_NO_INFER` 不执行，`SEPARATE_INFER` 和 DEFAULT ASIC 会执行；
- 使用独立 workspace，不替代拆分的 get_model/quant/compile 或后续标准 demo；
- test.sh 执行后，标准 demo 仍会独立准备/恢复 artifact；
- shell 与标准 demo 的失败最终合并进同一个 demo flow 结果；
- `enable_demo_test=false` 只在 release 模式阻止后续 Python/HMATC demo，不影响 development；
- CV test.sh 使用激活的模型 Python 环境；LLM test.sh 直接使用 `python3` 环境。

`test_sh_params` 支持三种布局。

参数组列表，每个内层数组是一条完整 argv：

```json
"test_sh_params": [
  [],
  ["--model_size", "1.7b"],
  ["--demo_mode", "streaming"]
]
```

按 backend 包装参数组列表：

```json
"test_sh_params": {
  "xh2": [
    []
  ]
}
```

列式对象：列表列按索引组成 case，标量值在每个 case 中复用；boolean `true` 生成 flag，`false` 省略：

```json
"test_sh_params": {
  "model_size": ["0.6b", "1.7b"],
  "streaming": [false, true]
}
```

空值或未配置时等价于执行一次无额外参数的 `bash test.sh`。

## 8. 模型 JSON 字段说明

### 8.1 顶层公共字段

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `obsolete` | boolean | `true` 时跳过 active schema 深度校验，但仍生成 pytest 函数和 marker；运行时所有声明 flow 都 skip。 |
| `model_dir` | string | 相对仓库根目录的模型源码路径，必须非空，不能是绝对路径或包含 `..`。 |
| `model_type` | `cv` / `llm` | 模型 family；决定 registry 和 family policy。缺省会按 `cv` 解析，但新配置应显式填写。 |
| `dependencies` | object | 资源 marker。目前使用 `ndevice`、`dev_mem` 数组；生成器使用每个数组第一个值。 |
| `support_platform` | string[] | 支持的平台，例如 `x86_64`、`aarch64`；当前平台不匹配时 skip。 |
| `support_backend` | string[] | 支持的 backend，当前 active 配置只允许代码 policy 中存在的 `xh1`、`xh2`。 |
| `support_core_num` | object/backend -> number[] 或 null | aarch64 demo 的设备 core 要求；无法满足时 skip。 |
| `support_flow` | object/backend -> string[] | 当前 backend 要生成/运行的 flow；合法七个 flow外还允许 `demo_multibatch`。 |
| `support_hmatc` | null 或 object/backend -> string[] | 兼容性能力说明，可列 `hmquant/hmbuild/hmdemo/hmcompare/hmeval/hmperf`；当前运行时不靠它选择实现。 |
| `validation` | object/backend -> object | 可选 cosine 覆盖，只允许 `compile_cosine_threshold`、`compare_cosine_threshold`，值必须在 `[0,1]`。 |
| `perf_metrics` | object | perf 基线；支持 backend 下直接指标对象或再按 platform 配置。声明 perf 时必须能为每个 backend/platform 解析出非空数字指标。 |
| `eval_threshold` | object 或 null | eval 指标名到 HM/ONNX 最低比例；声明 eval 时必须是对象。 |
| `enable_demo_test` | boolean | release 模式下，test.sh 后是否继续标准 demo；默认 `true`。development 不受 `false` 影响。 |
| `test_sh_params` | array 或 object | test.sh 参数组、backend 包装或列式对象，详见第 7 节。 |

### 8.2 标准 Python/get_model 参数 section

这些 section 除特殊说明外均为：

```text
section -> backend -> 列式参数对象
```

| 字段 | 含义 |
| --- | --- |
| `get_model_params` | 传给 `get_model.py`；常见 `type`、`model_dir`、`download_dir`、`extract_dir`、`quant_model_dir`、`build_model_dir`、`source_type` 和模型特有参数。 |
| `quant_params` | 传给 Python `ptq.py`；可含特殊键 `prerequisites`，该键不作为命令参数。 |
| `compile_params` | 传给 Python `build.py`；常见 `model_dir`、`output_dir`、`stage`、`batch`、`ncore`、`ndevice`、`context_length`、`j`、`model_size`。 |
| `demo_params` | 传给 Python demo；`script` 指定脚本名且不会渲染成 `--script`，未设置时默认 `demo.py`。 |
| `demo_multibatch_params` | 传给 multibatch demo；仅在 `support_flow` 声明 `demo_multibatch` 时执行，默认脚本为 `demo_multibatch.py`。 |
| `perf_params` | 当前通用配置只支持字符串 `"demo"`，表示 perf 复用当前 backend 的 `demo_params` 第一个 case；不是独立列式命令参数。 |

`quant_params.prerequisites` 可使用：

```json
"prerequisites": {
  "hm_gptq": true,
  "py_reqs": ["path/to/extra-requirements.txt"]
}
```

- quant 优先读取 workspace 的 `requirements_ptq.txt`，随后读取 `requirements.txt`；
- `hm_gptq=true` 时追加 `$HOUMO_EXAMPLES_PATH/hmodel/gptqmodel/requirements.txt`；
- `py_reqs` 的相对路径先在 workspace 查找，不存在时再相对 `HOUMO_DATASETS_PATH` 查找；
- 不存在的 requirement 文件会被忽略，不会作为命令参数传给模型脚本。

### 8.3 HMATC 参数 section

共享 HMATC section 使用：

```json
"hmquant_params": {
  "params": {
    "required": {},
    "optional": {}
  }
}
```

适用字段：

| 字段 | 命令 |
| --- | --- |
| `hmquant_params` | `hmatc quant` |
| `hmdemo_params` | `hmatc demo` |
| `hmcompare_params` | `hmatc compare` |
| `hmeval_params` | `hmatc eval` |
| `hmperf_params` | `hmatc perf` |

HMATC build 按 backend 配置，结构少一层 `params`：

```json
"hmbuild_params": {
  "xh2": {
    "required": {},
    "optional": {}
  }
}
```

`required` 和 `optional` 在执行前合并为同一个列式矩阵，两者所有列表列长度必须一致。字段名由 HMATC CLI 决定；框架会统一补充 `hmatc <subcommand> --target <backend>`，并跳过内部处理的 `target`、`onnx` 等字段。

### 8.4 参数矩阵渲染规则

例如：

```json
{
  "model_dir": ["cached_results/q1", "cached_results/q2"],
  "ncore": [1, 2],
  "fast": [false, true],
  "stage": ["build", "default"]
}
```

会生成：

```text
case 0: --model_dir <q1真实路径> --ncore 1 --stage build
case 1: --model_dir <q2真实路径> --ncore 2 --fast
```

规则：

- 同一列索引组成同一个 case；
- 所有列表列必须等长且不能为空；
- `null` 和字符串 `"default"` 省略该选项；
- boolean `true` 生成无值 flag，`false` 省略；
- 其他值生成 `--<JSON key> <value>`；key 原样保留，下划线和短横线不会自动转换；
- `cached_models`、`cached_results` 在渲染前替换为当前 `FlowContext` 的真实路径；
- `prerequisites`、`script`、HMATC 的 `onnx/target` 等由对应 handler 显式跳过。

### 8.5 flow 与必需 section

active 配置加载时会检查：

| `support_flow` 声明 | 至少需要 |
| --- | --- |
| `get_model` | 当前 backend 的 `get_model_params` |
| `quant` | `hmquant_params` 或当前 backend 的 `quant_params` |
| `compile` | 当前 backend 的 `hmbuild_params` 或 `compile_params` |
| `demo` | `hmdemo_params` 或当前 backend 的 `demo_params` |
| `demo_multibatch` | 当前 backend 的 `demo_multibatch_params` |
| `compare` | `hmcompare_params`，且 family 必须为 CV |
| `eval` | `hmeval_params` + `eval_threshold`，且 family 必须为 CV |
| `perf` | `hmperf_params`、`perf_params: "demo"` 或已有代码侧 custom runner；同时必须有可解析的 `perf_metrics` |

## 9. 新增或修改用例

### 9.1 新增模型

1. 复制 `model_configs/model_cfg_template_cv.json` 或 `model_cfg_template_llm.json`。
2. 保存为 `model_configs/model_cfg_<model_name>.json`；文件名决定模型名和 marker。
3. 设置正确的 `model_dir`、`model_type`、资源依赖、platform、backend 和 `support_flow`。
4. 为每个声明 flow 添加第 8.5 节要求的参数 section。
5. 所有参数列按 case 索引对齐，不要只增加某一列而遗漏其他列。
6. cache 路径使用 `cached_models/...` 或 `cached_results/...`，不要写机器绝对路径。
7. 运行生成器和检查：

   ```bash
   python -m tests.models_tests.update_test_py
   python -m tests.models_tests.update_test_py --check
   pytest tests/models_tests --collect-only -q
   ```

8. 在目标 backend/platform 上执行模型和 flow 的定向 smoke。

### 9.2 修改现有用例

- 只修改命令参数但不改变 `support_flow` 时，生成的 pytest 函数通常不变，但仍建议执行 `--check` 和收集检查；
- 增删 `support_flow` 后必须重新运行生成器，对应测试函数会增加或删除；
- 修改 `obsolete` 不会删除测试函数：`true` 运行时 skip，改回 `false` 后恢复执行；
- 如果当前 `test_<flow>_models.py` 与 JSON 不一致，运行不带 `--check` 的 `update_test_py.py` 会按当前全部配置全量更新；
- 不要在 JSON 中增加 flow 依赖、perf regex、指标方向、聚合方式、xh2 ncore policy 或通用失败词例外；这些属于代码 policy/handler。

### 9.3 混合 flow 模型检查清单

- `support_flow` 只声明真正要生成 pytest case 的 flow；
- 通过 `hm*params` 与普通 `*_params` 的存在关系选择每个 flow 的实现；
- HMATC 多 YAML 的所有 `model.save_dir` 必须相同；
- raw get_model 必须能在 workspace 的固定相对位置生成 HMATC 所需 ONNX/配套文件；
- Python compile 的 `output_dir` 与 demo 引用应指向同一逻辑 case；
- demo/perf 直接引用 `cached_models/<folder>` 时，应存在能匹配该参数行的 `get_model type=hmm` case；
- separate no-infer 与 infer 使用相同 backend、资源 marker 和模型 cache/result cache 布局。

## 10. 日志、验证和排错

### 10.1 命令输出

模型命令 stdout/stderr 会：

1. 实时读取，避免子进程 pipe 堵塞；
2. 写入当前 pytest case 的 `tests/test_logs/<date>/...log`；
3. 默认镜像到 pytest 进程。

要在终端实时看到镜像内容，pytest 还必须使用：

```bash
-s
```

或：

```bash
--capture=tee-sys
```

推荐：

```bash
pytest --log-cli-level=INFO -s -m "imodelzoo and ndevice_1 and dev_mem_12g"
```

如需只写日志而不镜像终端：

```bash
IMODELZOO_MIRROR_COMMAND_OUTPUT=OFF pytest ...
```

虚拟环境创建/安装命令也会镜像输出；模型脚本使用模型侧 `CommandSpec`，默认同样开启镜像。失败时优先检查终端中的命令尾部诊断和对应完整日志文件。

### 10.2 常见失败定位

| 现象 | 优先检查 |
| --- | --- |
| 模型脚本 import 时断言 `HOUMO_TARGET` | 当前进程环境和日志中的 backend；默认应自动同步为 `xh2`。 |
| `compiled artifact case ... is missing` | JSON 的 `compile_params.output_dir`、最终 `cached_results/<case>`、manifest 和非空 HMM；不要只检查 producer 侧 `cached_models`。 |
| `cached_models` 资源目录缺失 | demo 参数引用目录是否正确；是否存在可根据模型参数匹配的 `get_model type=hmm` case；get_model 是否实际生成该目录。 |
| HMATC inference 找不到 ONNX/YAML | raw get_model 是否运行；no-infer 的 `cached_models` 是否包含相对目录；infer 是否拿到相同 cache；YAML 是否位于 workspace 内。 |
| HMATC bundle 不复用 | YAML 内容/路径、backend、`model.save_dir` 或 fingerprint 是否变化；manifest 的 required HMM/with_act ONNX 是否存在。 |
| pytest 只显示 venv 日志 | 确认 `IMODELZOO_MIRROR_COMMAND_OUTPUT` 未关闭，并使用 `-s` 或 `--capture=tee-sys`；再检查完整 case log。 |
| 所有 xh2 compile case 被跳过 | 是否只有 `ncore=4`；需要时设置 `IMODELZOO_ALLOW_XH2_NCORE4=ON`。 |
| eval 指标比预期容易通过 | 未设置 `HOUMO_FULL_DATASET` 时阈值会乘 `0.5`。 |
| release 下 LLM quant/compile 被跳过 | 当前设计如此；检查 `USE_RELEASED_MODELS`，development 模式需设为非 `ON/on` 值。 |

### 10.3 提交前检查

```bash
python -m py_compile \
  tests/models_tests/test_models_utils.py \
  tests/models_tests/model_workflow/*.py \
  tests/models_tests/test_flows/*.py

python -m tests.models_tests.update_test_py --check
pytest tests/models_tests --collect-only -q
git diff --check
```

排错时先确认 `HOUMO_TARGET`、`USE_RELEASED_MODELS`、`SKIP_INFER`、platform 和资源 marker，再根据日志中的 `run_id/model/backend/flow/case_id/phase` 定位命令，最后检查 cache 目录、manifest identity、fingerprint 和 `required_files`。不要为了排错直接删除整个缓存根目录。
